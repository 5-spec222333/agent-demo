# 产品大图 v1 决策记录

## 本次交付

首版产品大图采用“业务决策链 + 分段可读”的结构，帮助产品新人理解业务顺序、人工确认点、平台生产能力、异常返回和数据去向。

## 已确认事实

- 业务必须从增长意图开始，经过 Agent 理解、追问、需求确认、选品与承接确认后，才能进入创意和生产。
- 图片与视频分链生产；视频由分镜、模型片段、TTS/数字人等组件和工程合成共同完成。
- 生产失败支持局部重试、降级和人工接管；审核驳回返回具体生产环节。
- 需求、创意、素材和审核的重大修改创建新版本，保留历史。
- 数据回流首期只做记录、比较和观察，不承诺自动归因与自主优化。

## 产品推断

- 将连续业务主链归并为七个阅读阶段，但不改变节点顺序。
- 主画布只放业务摘要，完整输入、处理、输出、状态、异常和追溯字段放在节点详情侧栏。
- 商品 List 同时表达主推 SKU、候补、推荐理由和排除原因。
- 承接对象区分商品页、店铺页、频道页和活动页；本案例使用虚构夏装活动页。
- 全链路追溯作为贯穿页面的独立轨道，避免被误解为某个单点系统能力。

## 实施取舍

- 使用原生 HTML、CSS、JavaScript 和集中 Mock 数据，保证离线可用。
- 主图采用单一综合视图，只展示业务域和模块名称；系统处理、状态和异常进入节点详情。
- 页面使用颜色、线型、箭头和文字共同区分关系，避免仅靠颜色传达含义。
- 采用大型电商增长产品视角审视方案，但不虚构京东内部系统、数据、规则或真实任职经历。

## 影响范围

- 前置确认闸门影响选品、创意和创建任务：商品与承接对象未确认时，不得进入批量生产。
- 版本机制影响需求、创意、分镜、审核和素材库：重大修改不能静默覆盖。
- 异常路径影响生产队列和审核队列：失败需定位到图片、镜头、组件或合成步骤。
- 追溯字段影响投放与分析：投放结果必须能关联到素材、商品、承接页和生产参数。

## 视觉重构记录

根据用户提供的大型电商产品全景图样式，页面从“绝对定位节点 + 逐节点曲线连线”调整为“左侧分层标签 + 阶段业务域 + 能力矩阵 + 聚合关系轨”。

- 保留原有 7 个阶段、7 条泳道、35 个节点、40 条关系及全部节点详情，不改变业务定义和状态逻辑。
- 黄金主链路放在大图顶部；每条泳道作为独立层级块，每个阶段作为带边框的业务域。
- 节点使用规整矩阵排列，人工确认、异常、资产、图片和视频仍保留不同视觉语义。
- 全景不再绘制 40 条交叉曲线，改用 5 条分类关系轨；节点的精确上下游在详情面板展示。
- 该调整降低连线遮挡和视线跳跃，不影响筛选、视图切换、缩放、导航、打印与全链路追溯。

### 第二轮版式修正

用户复核后明确：业务层无需与黄金主流程逐列对齐，但每一层必须铺满，不能用空阶段单元格维持形式上的列对齐。

- 黄金主链路仅承担端到端顺序导航，与下方各业务层共享整体左右边界，不再约束业务层内部列宽。
- 每条泳道只渲染实际存在的业务域；业务域根据所含模块数量按比例分配宽度并铺满整行。
- 删除所有空阶段占位格，保留统一的 8px 层内边距，使模块边界连续、职责清楚。
- 黄金主链路改用自适应七等分，修复固定列宽叠加外边距造成的第七列越界。
- 该模式采用常见互联网产品全景图的“主链在上、业务域居中、生产与数据能力分层支撑”构图方式，而不是流程泳道图的全局列对齐方式。

### 第三轮内容与语义收敛

用户要求主图进一步面向跨岗位协作，减少切换、技术语言和无连线的辅助区块。

- 合并业务、系统和状态三个视图为一个综合视图；主图模块只显示名称，其余信息统一放入详情侧栏。
- 删除“关键关系与返回路径”区块；40 条节点关系继续保留在数据层，并在节点详情中展示精确上下游。
- 隐藏节点内部编号；任务号、需求号、版本号和英文配置名在展示层转换为可直接理解的业务语言。
- 普通模块统一使用青绿色，避免无解释的综合色块。
- 白底虚线只表示资产与规则；图片、视频和队列使用文字角标标明类型。
- 在主链路下增加模块样式图例，颜色和边框不再承担未说明的隐含语义。

### 第四轮详情收敛

用户反馈完整规格式详情仍然增加技术与运营的理解成本，因此详情改为协作摘要。

- 删除业务说明、状态与异常、追溯信息三个页签。
- 详情只保留“目标”和“业务过程”两个正文区块。
- 业务过程将输入、系统处理、输出和业务人员动作合并为一句话。
- 详情不再展示“需人工”或“异常”标签；相关动作和处理规则只保留在业务过程与结构化数据中。
- 状态列表、追溯字段和上下游关系继续保留在结构化数据中，但不在当前详情界面展开。

### 第五轮业务动作收敛

- 删除全部“需人工”和“异常”角标、图例说明及详情提醒。
- 将原有泛化默认动作改为“无需操作”，由系统自动完成。
- 业务人员只在需求补充与确认、商品和点击页面、创意方向、预览版本、生产范围、自动恢复失败后的处置、审核结论、投放启停、效果复用和复盘沉淀等关键事项上作出判断。
- 模型路由、生成参数、队列日常调度、组件合成、自动质检、素材入库和数据关联不要求业务人员逐项确认。
